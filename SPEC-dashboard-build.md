# Spec: dashboard-build

Objective: turn one or at most two independent SQL results into a saved dashboard without any dashboard planning or summary model calls.

Approved bounded-query extension: new builds may receive two independently executable queries from the existing SQL generation call when one dataset cannot faithfully represent the requested grains. Ordinary single-query responses and deterministic SQL compilers stay unchanged. Validate the entire bundle before executing either query; retain the current schema, metric, permission and time-scope rules. Assign dataset/tile IDs on the server. Each tile references exactly one result; never join results or calculate ratios, deltas or totals between them. A database failure in one query leaves the other visible with partial status. Clarifications stay in chat. Refresh reruns saved questions individually and cannot create nested bundles. Existing legacy documents retain their current query capacity. Broader cross-domain support, cross-result calculations, presets and cost benchmarks remain separate work.

Request/representation rules (2026-11-15 follow-up): the existing SQL generation call interprets natural-language dashboard requests into source, metric, grouping, period and filters. Server-owned dashboard context tells that same call to distinguish data requirements from chart/layout/descriptive-summary wording; it must not add separate statistics datasets or invent totals. No extra interpreter model call or sales-specific parser is introduced. The original question and shared scope remain intact.

Choose one primary representation per dataset: an eligible temporal chart, categorical chart, separate aggregate KPI cards, or a table for explicit table/detail requests and chart-ineligible results. Add descriptive statistics only when explicitly requested and supported by multiple returned aggregate observations. A chart's expandable source-observations table is its data table; do not add a duplicate table tile. Descriptive summaries must not change metric definitions or reinterpret an explicit average as a presentation request. Preserve manually edited existing dashboards on refresh; Rebuild applies the current rules.

Shared scope is input, never generated content. Build, save, refresh, API response and editor display preserve the submitted scope. Reject response/request scope mismatches in the browser instead of silently replacing the editor. Disable scope autofill and clear creation fields on New/successful build. Verification covers independent description/scope inputs, previous dashboard output in preview HTML, persistence/reopening, and no extra model calls. The reported long-text overwrite has not been reproduced in stored data; do not claim a root cause without evidence.

Inputs: server-verified analytics identity, description (2,000 characters), optional shared scope (600 characters). Forward the complete description and scope once to the existing SQLAnalyticsAgent.run_payload. SQL owns schema discovery, interpretation, validation and execution. Do not call the AnalyticsAgent narrative wrapper.

Output: typed dashboard document with one or two independent datasets, SQL/parameters, evidence, policy/metric metadata, observed dates, tile configuration, status and timestamps. Keep the existing SQL security boundary and 180-second build budget. Choose tiles deterministically: separate KPIs from a single ungrouped aggregate row; eligible line/bar/donut charts; explicitly requested descriptive statistics of aggregate observations; source observations without a duplicate table tile. Never sum grouped rows into an overall KPI or interpret IDs as measures. Explicit incompatible charts retain their fallback reason. Partial source failures and empty results remain visible. SQL clarifications and incompatible requested charts stay in chat before saving. A deterministic compatibility check tests alternative line/bar/donut/table representations against the actual result and explains valid choices. User replies can change presentation; refresh retains other edited tiles and revision checks.

Implementation: `src/core/dashboards/models.py`, `agent.py`, `presentation.py`. Reuse the SQL agent, runtime deadlines, chart mapping, renderer and store. No separate dashboard model call; bounded decomposition occurs only within the existing SQL generation call. Retain the legacy chart-preview route and refresh support for existing multi-dataset documents.

Refresh preserves edited tile definitions and reruns their saved questions with the current shared scope, without a model rewrite. Recognized conflicting explicit periods require editing the description and Rebuild; keep dates in shared scope when users need to change them frequently. Rebuild creates at most two independent datasets and new automatic tiles under the existing saved identity. Presets and decomposition beyond two independent datasets are deferred.

Style: strict Pydantic models; `await sql_agent.run_payload(scoped_request)`; never interpolate model/user text into executable SQL.

Verify: `.venv/Scripts/python.exe -m unittest discover -s tests -p test_dashboard*.py`. Test no additional model calls, real SQL validation with mocked transport, permissions, scopes, saved documents, chart fallbacks, numeric strings, NULLs and empty/failed results. No external model calls in unit tests.

Always enforce identity, query limits, deadlines and result provenance. No new external provider or analytics-schema migration. The underlying SQL agent can still make model calls; only dashboard composition is model-free.

Mixed-chart clarification fix (2026-11-15): the existing SQL generation call can return at most two per-chart mappings in request_contract.charts for each dataset. Each mapping declares a line/bar/donut type, one returned dimension and one to four returned measures. Validate mappings before SQL execution; mappings cannot add fields, dependencies or executable content. Shared-grain charts reuse one SQL result. Preserve mappings through execution and persistence, and render each chart using its own fields and type. Missing mappings for a mixed-type request remain a clarification in chat, not an HTTP error or guessed association. Show source observations once per shared dataset. No source, metric or request-phrase special cases.

Per-chart descriptive-summary fix (2026-11-15): run shared summary composition after primary tile selection and presentation choices, for both single and mapped multi-chart results. When explicitly requested, add one summary per eligible chart using only that chart's returned aggregate measures and dataset. Do not include identifiers, grouped dimensions or window calculations. Require multiple returned observations, preserve NULLs, keep unique dataset-scoped IDs and share source observations once. The original summary request must survive query decomposition and presentation-only clarification replies. No new SQL/model calls or metric/source-specific conditions. Rebuild applies automatic summary selection to saved dashboards; refresh preserves existing tile definitions.

Aggregate-lineage follow-up (2026-11-15): summary eligibility follows SQLGlot column lineage through CTEs and derived subqueries, including renamed and unqualified transparent projections. An outer SELECT of an aggregate alias retains the aggregate role. Raw fields, grouped dimensions and outputs with window functions anywhere in their lineage remain excluded. Verified against the actual saved five-month traffic query by replaying its stored rows without an analytics query or model call.

Output-completeness extension (2026-11-15, approved): new model-generated dashboard builds must include an outputs manifest in the existing SQL JSON response, covering every explicitly requested and automatically selected representation. Each entry binds one of line/bar/donut/table/kpi/summary to a zero-based query index, returned measure aliases, a dimension where needed and optional summary group_by fields. Server assigns tile IDs. Keep at most two independent queries and eight total outputs. Validate the entire manifest and all SQL before executing: references/aliases, dimensions, aggregate lineage, scalar KPI grain, no window/raw-field summaries, shared period and supported representations. Overall totals must be queried at overall grain rather than summed from chart rows. Summaries can use returned aggregate measures without requiring a chart. Grouped descriptive summaries (statistics within each month) remain unsupported and must ask for clarification instead of becoming global statistics. Model-generated missing/invalid manifests get the existing one repair opportunity and then a clarification with no execution. Ordinary non-dashboard SQL and saved refresh layouts retain their paths. New non-inventory dashboard builds use SQL generation to declare outputs even when a deterministic compiler could previously have supplied only the data; there is no separate planning call. Typed inventory compilation obtains the output manifest alongside its existing interpretation call.

Render exactly the declared outputs and check runtime suitability for every declared representation before saving. No automatic truncation/table substitution of declared outputs. Empty/source-failed outputs retain explicit state; incomplete renderable requirements stay in chat. Preserve existing partial source-failure behavior and owner/revision/clarification limits. Refresh retains edited tile bindings and may refresh rows but not replan outputs. No added planning, narrative or requirement-extraction model call. Natural-language interpretation is still performed by the existing SQL model; manifest validation proves SQL/output consistency, not perfect interpretation of arbitrary prose. Verify generic renamed measures/sources, total+trend+summary in two queries, unsupported grouping/representation, missing bindings, wrong date scope, CTE lineage, no execution before validation, retry/clarification, and persistence/refresh.
