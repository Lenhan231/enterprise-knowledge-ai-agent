# Spec: dashboard-workspace

Objective: add a separate Dashboard tab to the local web app. The current user explicitly chose the app rather than Streamlit for this workspace.

Clarification chat (2026-11-15): replace the initial description card with a chat-style transcript and composer using the General Chat visual patterns. Keep optional scope separate and fixed while clarifying. Submit the original request to the existing SQL workflow once per user turn; no additional clarity/planning model. If SQL asks a question, show it as an assistant message, keep the composer available, retain original description/scope plus server-owned question/reply history, and do not save a dashboard or show editor/preview. After a usable query result, save once and open the workspace. Source failures stay in chat without creating artifacts.

Reuse ConversationStore with owner/permission isolation, expiry, bounded capacity, and at most three clarification replies. Clients send only a message and opaque conversation id; assistant questions and target dashboard identities come from server state. Expired/foreign/stale continuations must not query or mutate saved dashboards. Rebuild/refresh continuations retain owner checks and optimistic revisions. Reopening an older saved clarification starts a transient chat draft without a model call; it is replaced only after successful clarification. Restarting the server can expire drafts, consistent with existing process-local conversations. Conversation history is context, never source evidence.

The chat remains visible while the same SQL call checks and executes the request; the workspace opens when usable results are available. Do not add a separate preflight call merely to switch screens sooner. Keep existing saved-library, presentation edits, HTML sandbox and private export. Test multi-turn clarification, no failed artifact persistence, owner/role/expiry isolation, stale-target conflicts, failed retries, UI transcript escaping, New/account reset, no premature workspace, and Enter/Shift+Enter behavior.

Workflow: describe a dashboard → build and save → preview one HTML document → reopen from saved list → edit title/tile titles, layout order/span and supported chart type/columns → save a revision. Data-scope filters trigger SQL refresh without a dashboard model call. Conflicting explicit periods require updating the description. Rebuilding an edited description regenerates tiles from at most two independent SQL results; refreshing an unchanged definition reruns its data questions. Open/download HTML and delete owned dashboards are available.

UI: reuse the existing sidebar, role visibility, API client, authentication lifecycle and design tokens. Responsive library/editor/preview layout, labeled controls, keyboard-accessible actions and explicit busy/error/partial states. Clear private state and ignore late responses after account/session changes. Use an iframe sandbox; no HTML in the privileged app DOM.

Implementation: `src/app/static/dashboard.js`, `dashboard.css`, small `index.html` and `app.js` integration. APIs are `/api/dashboards` and owner-scoped item/refresh/html routes. Both app and backend are served by the existing local FastAPI process at port 8000. Stop the earlier owned Streamlit process; do not launch another Streamlit instance.

Verify: `node --check src/app/static/dashboard.js`, `.venv/Scripts/python.exe -m unittest discover -s tests -p test_dashboard*.py`, HTTP health/authenticated CRUD smoke checks, and browser UI review if a browser surface is available. No frontend framework or dependency is added.

Chart compatibility (2026-11-15): successful SQL is insufficient to open the workspace when a requested chart is unavailable. Keep the request in chat, explain the renderer reason and suggest only alternatives verified against the returned data. Do not save an unavailable requested chart automatically. A reply can select a supported representation or narrow comparable measures through the existing SQL turn. The compatibility check uses no model. Refresh replies update the affected tile while retaining other presentation edits. Partial database failures remain visible when another independent query succeeds.
