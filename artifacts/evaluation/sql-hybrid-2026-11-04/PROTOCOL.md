# Minimal hybrid evaluation

Production stays at the source behavior of `ac0d8a2` (unchanged from `f48bec5`). The candidate is an isolated patch to the existing SQL agent, not a duplicate agent or a new LLM routing layer. Its only new branch recognizes complete explicit field requests and checks generated SQL against a SQLGlot AST parsed independently from the request. Canonical inventory metrics retain the original LLM mapping and deterministic compiler. Both direct and existing generic SQL retain one bounded repair attempt. RBAC, approval/formula checks, SQLGlot, approved joins and the read-only repository remain unchanged.

Direct eligibility is deliberately narrow: stateless `List/Show/Retrieve <field names> from [commerce.]products|inventory`, literal AND filters/IN/NULL checks, field ORDER BY and LIMIT. Inventory direct fields are only snapshot_date, product_id, year and month; any inventory measure remains on the canonical path. Product price/cogs are raw source fields, not company COGS, inventory valuation, an inferred currency or an approved KPI. Expressions, joins, aggregates, unknown fields and partially parsed clauses do not receive direct execution. Stable primary-key ordering and the existing 200-row ceiling apply. The field guard checks exact projections/source/population, every date/filter, ordering and bound after parameter resolution, with harmless syntax normalization. Invalid generated SQL can be repaired once; it cannot silently lose a constraint.

All 30 original frozen questions fall outside this explicit-field grammar. Re-running unchanged provider paths is unnecessary: replay the existing production LLM responses through the hybrid and the actual read-only repository, require identical SQL/parameters/result multisets/status/answer and exactly the same response count, then report inherited baseline metrics per category. Label these as replay-verified baseline results, not fresh generation, new Ragas judgments or new end-to-end latency. Original questions/references/scorers/judge are untouched.

Separate categories are fixed before generation: 13 canonical inventory requests, 4 inventory diagnostics, 8 commerce analytics, 3 cross-domain calculations, 2 unsupported requests. The IDs are recorded in the separate field-fixture manifest and are evaluation labels only.

Six additional direct-field questions are predeclared in `evaluation/run_sql_hybrid_evaluation.py`, independently authored against approved raw fields. Freeze `direct-fields/cases.jsonl` and `oracles.json` before any provider generation. These supplement, never replace or edit, the original frozen benchmark. They cover two inventory metadata requests, three product numeric-field requests, and one product-attribute request. Product numeric fields use stored raw units; no metric formula changes or currency conversion. References are author-reviewed fixtures, not externally certified gold.

Run fresh production and hybrid generation/scoring on these six questions with the existing Ragas library, unchanged custom execution/numerical metrics and SQLSemanticEquivalence, same CodexCLIJudge gpt-5.6-luna/medium, same Groq model/temperature and existing three-key quota fallback. Retain all attempts; only retry provider errors. Numerical applicability and scored denominators must be explicit. Do not combine replay latency with fresh provider latency or claim global speedups from six field questions.

Adversarial tests independently mutate fields, literals, dates, source, filters, ranking, row bounds and calculations. Verify writes/private sources are blocked, canonical metric requests still map/compile, the prior blue-stock filter regression is blocked, and direct SQL gets at most two generations including repair. Unknown field-request clauses fail with clarification rather than partial interpretation. Existing complex-join safety tests remain authoritative.

Adoption requires non-inferior results and safety within the demonstrated categories. Finite tests do not prove arbitrary natural-language intent; unsupported language retains production behavior or needs clarification. The grammar already provides a deterministic field contract, so the additional SQL generation call may itself be redundant; measure its cost rather than claim architectural simplification. Keep production unchanged and give a scoped recommendation after results.
