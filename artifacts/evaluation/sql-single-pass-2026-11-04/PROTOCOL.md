# Isolated single-pass SQL experiment

Production source is frozen at `f48bec5`. No production source, routes, schema, permissions, metric definitions or scoring code is edited. The experiment is a reviewed patch in a detached checkout: `evaluation/sql_single_pass.patch`. It removes mandatory LLM metric mapping, deterministic inventory compilation and SQL repair from that checkout only. It retains the existing agent interface, authorization, current-period/source-policy preflight, catalog validation, SQLGlot/join validation, repository revalidation, read-only execution and result assembly. There is one SQL generation response per attempted request; provider transport retries/failovers are counted separately by the inherited harness.

The small evaluation-only `sql_single_pass_contract.py` reuses existing AST helpers to check explicit dates, literal field predicates, product IDs, NULL populations, ranking and bounds. It cannot prove arbitrary natural-language intent. Ordinary approved inventory/product field queries are permitted without requiring a catalog mapping; invented metric calculations remain subject to catalog checks. Server conversation state is explicitly unsupported in this stateless experiment.

Run one fresh production cohort and one fresh single-pass cohort on all S01-S30, in the same order. All questions are stateless and eligible. SQL accuracy denominators exclude only the two pre-existing unsupported gold cases S29/S30; their refusals are reviewed separately. Original frozen SQL, results and questions are reused byte-for-byte from the main workspace. Recheck 28 supported reference results before generation. No successful generation or semantic failure is silently retried; retry provider failures only and retain attempts.

The model, temperature, Ragas library, inherited execution/numerical scorers and `CodexCLIJudge` (`gpt-5.6-luna`, medium) are unchanged. Primary Groq key, numbered backup and GROQ_API_KEY_RAGAS retain their existing order. Each cohort records application revision/source hashes, evaluation code hashes, raw generations/calls/scores, provider failures and latency. Production runs before the variant; this is a sequential paired comparison, not a controlled randomized latency experiment.

Adversarial fixtures run against both paths, injecting the same SQL after production's mapping/compilation boundary or directly as the variant response. They cover RBAC, write/private-table attempts, formula/date/filter/rank mutation, multiplicative fact joins, NULL substitution and ordinary fields. A separate SQLite fixture measures free-text population-filter loss on unequal blue/red product stock. A test recording a known gap is measurement, not a security pass. No adversarial SQL is executed against the remote database.

Report compatibility uses the actual shared-SQL evidence path, validated facts, narrative claim validation and both Markdown/DOCX assembly, initially with deterministic providers/repository fixtures. A separate read-only integration replay may verify the same contract with captured SQL and real database rows. This is not a Report quality benchmark or evidence that its separate planner no longer uses mappings.

Adoption requires observed non-inferiority in each of execution, numerical and strict semantic accuracy, valid refusal rate, and no new safety/semantic fixture regression. Compare numerical means both with inherited applicability and the common applicable-case intersection. Latency or fewer LLM calls cannot offset correctness/security regressions. Thirty cases and finite adversarial tests cannot prove general non-inferiority. Keep production unchanged regardless of outcome; recommend adopt, modify or reject only from measured evidence.
