# Strict Sales Performance Report

## Editable report workspace (November 18 update)

Named month ranges are inclusive: `Monthly revenue report from Jan to May 2026` queries `[2026-01-01, 2026-06-01)` with five monthly buckets. Full names, `between January and May`, hyphenated month ranges, and explicitly dated cross-year ranges use the same parser. Conflicting dates and reversed ranges require clarification. Single-calendar-month requests default temporal widgets to KPI presentation in preview, editor, saved reports, and PDF; explicit user chart choices override that default. Metric definitions and canonical SQL datasets remain unchanged.

The Reports tab has its own saved-report sidebar, independent of Dashboard. Generating through `/api/reports` saves the server-generated canonical JSON and a separate presentation document. Users can rename reports, reorder/remove/restore sections, edit executive-summary or findings prose, and switch charts between line, bar, KPI, and table. The default delivered-line view is a KPI; duplicate dashboard KPI rows are omitted from the report presentation. These are view overrides: the supplied immutable template, formulas, SQL results, source evidence, and deterministic rules stay unchanged.

VND is a user-requested display label, with no exchange-rate calculation or assertion that the source independently records VND. Compact numbered links appear throughout the preview and jump to Sources below the report. Technical units and query hashes stay out of the visible copy. Coverage issues and source errors are collected under Data notes. PDF downloads include the selected section order, hidden sections, narrative edits, and chart representations, omit citation markers and the Sources appendix, and retain material data limitations. A requested saved revision must still match before PDF export.

Report APIs require the existing analytics permission, use the verified account subject, enforce same-origin writes, and accept presentation edits only. The original report cannot be sent back as client-authored facts. PostgreSQL uses the existing least-privilege owner context with a separate `dashboard_private.reports` table, forced RLS, and a report-only owner policy. Dashboards and reports never appear in each other's library. SQLite development storage uses a separate report directory. Saves use optimistic revisions and the existing artifact size and per-owner limits.

Investigation of the live source found daily company sales from 2025-11-14 through 2026-11-13: 48 records in 2025 and 317 in 2026. A full-calendar-year revenue change is therefore unsupported; the current-year revenue is an observed partial-period total. SQL now returns both observed and expected day counts so the report states the precise coverage reason. Current-period gross-profit rules still evaluate when their inputs exist. An undefined zero-denominator change and an unsupported dimension get distinct data notes rather than an invented comparison.

Workspace actions share a busy/session guard. Save and download lock mutable controls, stale responses cannot replace a newer session or clear its authentication, and downloads are pinned to the saved revision. Generation status comes from the backend so failed chart queries remain partial. PDF rendering uses the installed PyMuPDF library without new dependencies.

Additional verification: `python -m unittest discover -s tests -p test_saved_reports.py` and `node tests/test_report_workspace.cjs`. Opt into live persistence tests with `REPORT_POSTGRES_TEST_URL`; the test creates randomly owned test reports and deletes them on completion.

The original implementation notes below describe the canonical contract and legacy endpoints; their immutable-layout rules apply to canonical data, while the new workspace adds the explicit presentation overrides described above.

The report form accepts one request, for example `Monthly revenue report for May 2026`, `Quarterly sales report Q2 2026`, or `Monthly revenue report in 2026`. It renders the five fixed sections, ten metrics, and six widgets from `data/semantic/sales_performance_strict.json`. This file is a byte-for-byte copy of the supplied version 1.1.0 contract. It is data, never an instruction source for executing tools.

When source options are omitted, dated sales requests automatically select analytics; an explicit document source selection is preserved. The form posts the question to the existing `/api/agents/report` endpoint with server-supported sales/analytics options. The development `/api/report` endpoint shares the same implementation and response. Successful sales requests return the runtime template JSON directly, with `X-Report-Status: complete|partial` and `Cache-Control: no-store`. Invalid or ambiguous periods return 422; missing verified analytics permission returns 403. Missing sources retain every metric/widget/section with unavailable values and explicit limitations. Legacy document templates and inventory reports retain their existing API paths; sales analytics rejects uploaded custom templates.

`core/reports/sales_performance.py` resolves calendar bounds and assembles and validates output. `core/agents/sql/sales_report.py` owns fixed SQL plans and calculations. The existing SQL Agent authorizes every query; its configured table scope and CommerceRepository enforce the SQL allowlist, joins, read-only connection, statement limits, and least-privilege Supabase role. There is no service-role fallback, schema migration, or new dependency. The Dashboard Agent's fixed-widget adapter copies SQL datasets into the prescribed widget order and types. The Report Agent copies values rather than performing business arithmetic.

Periods use `[start, end_exclusive)`. Named months without a year use the current year in Asia/Ho_Chi_Minh. Year-only requests such as `sales performance in 2026` cover the full calendar year and default to monthly chart buckets. Explicit annual/yearly or quarterly wording retains that requested granularity. Inclusive year ranges such as `from 2025 to 2026`, `between 2025 and 2026`, or `2025-2026` cover January of the first year through December of the last year; reversed and conflicting ranges are rejected. Latest resolves against the latest authorized observed company sales date. Product breakdowns use product IDs to avoid merging products with the same name. Explicit quoted dimension filters (product filters use IDs) and `by category|region|product|order source` are supported; unsupported metric/dimension combinations stay null. Company sales, delivered order-line sales, discounts, and traffic remain separate sources. Currency is unspecified.

Current and previous company periods require every daily observation before period-over-period change or comparison decisions can be evaluated. These daily counts verify coverage; comparisons use calendar-month totals. The canonical aggregate KPI compares equal-length calendar windows. Monthly report previews and PDFs show the latest observed month's change against its preceding month, with both months in the KPI label; incomplete coverage remains explicitly unavailable and does not silently select an older month. Full-period totals and canonical facts are retained separately. Explicit annual/yearly and quarterly reports retain their aggregate comparison. Decision Support in newly generated report documents evaluates the same S01–S04 rules separately for every month in the requested period, using its preceding calendar month (including the month before the requested start). One grouped, validated company SQL query supplies monthly values and coverage; it shares the aggregate metric formulas. Missing months and zero prior revenue remain unevaluable for growth rules; current-period profitability still evaluates when its inputs exist. Monthly results are server-owned metadata outside the immutable canonical contract, persisted alongside presentation edits and included in preview and PDF. Existing saved snapshots remain readable and unchanged; regenerate them to obtain monthly evaluations. Requests are bounded to 200 calendar months to match the existing chart/data limit. Sparse orders and traffic do not prove period completeness; that limitation is always disclosed. Missing aggregates and zero-denominator ratios remain null. Observed zero values remain zero. Charts preserve null gaps, and a 200-row limit is disclosed when reached.

Narrative slots are factual observations of validated metric values with query citations; they never infer causes. No LLM is needed for this fixed contract. S01–S04 are evaluated in backend code without `eval`, and incomplete prerequisites leave a rule unevaluated. S04 cannot claim no risk when another rule is unevaluable. The validator checks ordered keys, metric definitions, widget configuration, fixed slots, numeric types, evidence, and deterministic decisions before delivery. The browser renders source strings as text and includes data tables and evidence alongside charts.

For SQL arithmetic integration tests, set `SALES_REPORT_TEST_URL` to an explicitly approved read-only PostgreSQL connection and run the sales tests. They use inline CTE fixtures inside read-only transactions, create no tables, and write no data. Tests cover formulas, delivered-order denominators, missing days, zero denominators, source separation, period structure, authorization, immutable definitions, widgets, and decisions. UI and session tests run the shipped JavaScript with Node.

Sales reports also call the existing role-scoped `KnowledgeAgent.retrieve` with the resolved period. Bounded qualitative source excerpts, SQL coverage dates, and derived insights live in the saved-report wrapper, leaving the canonical template unchanged. No document number becomes a report metric, no retrieved text changes a decision rule, and excerpts are presented as context without inferring causality. Saved excerpts are reauthorized against current source ACLs before reopen/edit responses and PDF export. Retrieval timeout, access denial and no usable evidence are reported distinctly. Supported monthly actions appear first, all rule evaluations remain accessible, and exact missing-date requirements are listed below the report. See [data needs](sales-performance-data-needs.md).
