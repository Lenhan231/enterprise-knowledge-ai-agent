## Before running migration 003 in another environment

- Obtain approval to mutate the target database; do not rerun migration 001
  against an existing table.
- Confirm the vector extension is in `extensions`, supports HNSW, and the
  embedding column is vector(384).
- Recheck duplicate `(document_name, chunk_index)` and SQL NULL metadata.
- Check definitions and validity of both named indexes. `IF NOT EXISTS` only
  checks names, not equivalent definitions. The unique index name matches the
  name generated by migration 001's unique constraint.
- Use an approved maintenance window: regular index creation and ALTER TABLE
  take locks. Migration 003 uses one transaction with lock/statement timeouts;
  stop on error and roll back. Re-running on the intended schema is safe.

The SQL deliberately fails on bad preconditions instead of repairing rows.
`NOT NULL DEFAULT '{}'` does not guarantee metadata.document_id exists.

## Read-only integration check

Run only after approval to connect, with DATABASE_URL in the environment or
repository `.env`. Do not put credentials in command arguments or logs:

```bash
uv run python scripts/check_vector_repository_integration.py
```

The script uses a read-only, repeatable-read transaction. It reads catalog
definitions and data counts, uses an existing nonzero embedding, and exercises
the real repository method against reference SQL. No model download, test-data
insertion, sequence consumption, migration or persistent data change occurs.
It rolls back and closes the connection. Output includes only statuses/counts;
raw exceptions, source content and connection URLs are suppressed.

Exit codes: 0 = all checks pass; 1 = schema/data/mapping requirements unmet;
2 = configuration/connection/query failure. An empty corpus is not a successful
retrieval check. Unit tests mock the connection and never contact Supabase.

The mapping check disables index scans locally to compare deterministic exact
results, including ties, scores and full content. HNSW definition is checked
separately. This is not proof of planner usage, ANN recall, model compatibility
or semantic retrieval quality. Review EXPLAIN for the actual distance + id
ordering separately; a small table may reasonably use a sequential scan.

The earlier audit found 360 rows, including 25 without document_id. The
read-only check after syncing main found 302 rows and no missing IDs, duplicates
or SQL NULL metadata. That database change happened outside this work. Recheck
immediately before migration; the script fails if missing IDs return. If a
sampled row fails model validation, it reports `validation_failed` without
exposing content.

The read-only integration check passed against the audited Supabase database
after migration 003: vector(384), metadata NOT NULL/default, both indexes,
302 rows, no duplicate keys, no missing document IDs, and repository retrieval
mapping all passed. `EXPLAIN` also used the HNSW index for the repository's
distance-plus-ID ordering via an incremental sort. This does not verify ANN
recall, model compatibility or semantic quality, and does not by itself mark
all of SCRUM-13/SCRUM-14 Done.
